# 10 统一断语结构与写作质量

## 一、作者源稿结构（`authoring/<问事>/<script_id>.json`）

| 部分 | 要求 |
|---|---|
| `chart_input` | 六爻值（初→上）、月建、日辰。匹配键 = 问事 + 六爻值 + 月建 + 日辰 |
| `judgment` | 先写判断再写文字：结论类别（likely-pass / pass-but-slow / wait-then-likely / unlikely）、用神位置、决定性证据、支持证据、反面证据、冲突取舍、规则编号 |
| 标题 | 直接回答所问，体现本卦核心特点；不得写「吉凶参半」「事有变化」 |
| 简断 | 60–120 个汉字；主要倾向、最关键的帮助或阻碍、后续变化、一条现实建议；不堆术语（术语 ≥3 个给出提示），不写日期 |
| 详断·开局 | 用神、世应与日月条件：为什么目前是这个状况 |
| 详断·过程 | 动爻、原神、忌神、飞伏等真正影响本问题的证据；围绕证据组织，不逐爻机械讲 |
| 详断·结局 | 用神最终状态与关键条件，说明有利条件是否足以克服阻碍 |
| 应期 | 独立一栏，见 09 |
| 总断 | 明确结论 + 最关键依据 + 行动建议 |
| 古籍依据 | 每条：规则编号、书、卷章、逐字引文、本次适用理由 |
| 计算说明 | 专业事实，用户需要时才展开；构建另附引擎生成的卦盘事实表 |

## 二、文风

像一位懂六爻的老师在讲：语气平实、句子流畅、结论直接、证据清楚。每个术语第一次出现时说明它在这个问题里意味着什么（例如「旬空的意思是『此刻不在』」「子孙在求职卦里是克官之神」）。

严禁单独以下列句式构成解释：「用神旺，所以吉」「忌神克，所以凶」「存在一定帮助，但仍有阻碍」「综合各项因素，情况比较复杂」「按规则加权计算」「这里不能重复叠加」「模型认为」「源力待核」「这一项取最高评分」，以及「还要综合考虑」一类逃避结论的套话。构建脚本对这些短语与「程序、算法、引擎、概率、保证、百分之、R-」等内部用语一律拦截（C06）。

不得虚构：已发生的现实事件、对方真实心理、人物身份、具体金额、已确定的录用结果、具体地点、成功概率、古籍案例反馈。象意推断须带「从卦象看」之类的限定（IP-0006 自查记录）。

## 三、自动检查（`npm run build:readings`）

C03 用神与引擎一致；C04 必填；C05 简断字数；C06 禁用语；C07 简断无日期；C08 无公历日期；C09 正文中的「某日」只能是起卦日；C10 应期地支在规则候选内、说明与条目一一对应；C11 标题、简断、总断与结论类别一致且无相反措辞；C12 古籍引文逐字核对、规则已登记、写明适用理由；C13 每个动爻在详断中讲到；C14 跨篇不得有 14 字以上的重复句；C15 判断引用的规则已登记；C16 简断术语密度提示。

技术检查全部通过只记为「技术核验通过」，不等于专业审核。

## 四、状态与审核

1. 已完成基础事实（构建可重算）→ 2. 作者初稿（`authoring.status = draft-complete`）→ 3. 作者全文复核（`review/records.json` 中 `author-full-text-review`）→ 4. 技术核验（构建自动）→ 5. 专业规则审核（`professional-review`，审核者不得为 AI）→ 6. 发布批准（`release-approval`，须先有专业审核）。

记录绑定 `content_hash`：改稿后旧记录自动失效。发现矛盾时先记录问题、独立复算、确认规则、确定结论，最后改文字；不得先改结论再找卦理。
